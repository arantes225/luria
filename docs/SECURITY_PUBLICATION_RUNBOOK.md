# TRAUBE — Public release and credential incident playbook

## Important limitations

- GitHub repository visibility is currently public and GitHub Pages serves the site.
- A public GitHub repository exposes tracked content and *all reachable Git history*, regardless of static-site build filters.
- The static build denies internal question-factory snapshots, marketing workspaces, editorial drafts and image-curation imports. Those files remain accessible **in the GitHub repository until it becomes private** and may remain in old Pages builds/CDN caches.
- Apostila `content.json` files and intentionally public weekly-question JSON are still distributed to browsers. A login prompt cannot secure content delivered by static hosting.
- Client-side 4-digit PIN validation in the shift-manager UI is only a convenience lock. Do not rely on it for authorization. Protected backend data must enforce per-user authorization and RLS.

## Immediately after merging

1. Check GitHub Actions `Secret scanning` (Gitleaks) on `main`; manually trigger it if needed. Investigate all findings *without posting values in issues or chat*.
2. If a credential might have been committed, revoke/rotate at its provider immediately (Supabase secret/service-role, AI providers, Cloudflare SFU, Metricool, Asaas and any other matched service). Deleting commits alone does not revoke credentials.
3. Verify that a fresh Pages artifact excludes `qf-*`, `marketing/` and internal apostila editorial files. Test existing public pages, Admin, Study Rats, apostilas and weekly question delivery. Allow for CDN/browser caching.
4. Do not disable the live Pages site by making the repository private before configuring a replacement deployment. GitHub Free Pages requires public repositories.
5. Deploy the static build through Cloudflare Pages (or another host supporting private GitHub repos) with the same domain and Pages build output `build/pages` generated by `node scripts/build-pages.cjs`. Confirm DNS/SSL, PWA cache, user login and payment redirects before switching.
6. Once the replacement is healthy, set the source repository to private in GitHub Settings. Review public forks and old copies; privacy cannot retroactively erase forks/clones.
7. Move commercially protected apostilas, paid questions and answer keys behind authenticated server routes/private storage with authorization, download restrictions, rate limits and audited RLS. Browser-delivered content can always be copied by an authorized user; prevent anonymous bulk download, not all copying.
8. Review Supabase security advisors and `SECURITY DEFINER` RPC grants individually. Some privileged RPCs are intentionally callable by authenticated users; their implementations must verify ownership/admin status.
9. Rotate credentials and ensure future secrets live only in provider-managed environment settings, never in git, `.env.example` or browser bundles.
10. If a secret exposure is confirmed, consult a security specialist before attempting history rewrite. Rewriting git history breaks SHAs/branches and does not erase known external copies.

## Scope of these code changes

- Hardened `.gitignore` to discourage future accidental commits.
- Added fail-closed static artifact exclusions for internal areas.
- Added automated regression checks for excluded paths.
- Added Gitleaks Git history scan.
- No production data migrations, credential rotation, repository visibility updates or infrastructure/DNS changes are performed by this change.
