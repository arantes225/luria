## 2024-05-18 - [PostgreSQL Search Path Hijacking in SECURITY DEFINER Functions]
**Vulnerability:** Found `SECURITY DEFINER` functions across multiple files that either lacked a `SET search_path = ''` directive entirely or used an unsafe `SET search_path = public, pg_temp` configuration.
**Learning:** `SECURITY DEFINER` functions run with the privileges of the user who created them. If the `search_path` is not securely locked to an empty string (`''`), an attacker could potentially manipulate the search path to force the function to use malicious objects they created, leading to privilege escalation (CVE-2018-1058). When fixing these vulnerabilities, it is critical *not* to modify historical migration files, as they are immutable and altering them can break CI/CD checksums and existing database states. Instead, always create a new incremental migration file. Furthermore, when enforcing an empty search path, ensure that all internal object references within the function body (e.g., tables, other functions) are fully schema-qualified (like `public.table_name`).
**Prevention:** All PostgreSQL `SECURITY DEFINER` functions must explicitly append `SET search_path = ''` to their definitions. Always resolve vulnerabilities by creating new forward-rolling migration files rather than editing old ones, and rigorously schema-qualify all object identifiers within the function.
